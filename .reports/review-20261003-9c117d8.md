The most consequential implementation paths are a pre-dispatch failure escaping the entire Task scheduler and a runtime-retirement race that can report a failed submission after its Task has completed. - **High-confidence candidates:** The current source establishes the mechanism, supported here by deterministic execution or direct contract evidence. These remain review candidates rather than declarations of universal native-runtime behavior.
- **Plausible candidates:** The mechanism or specification gap is concrete, but an environmental condition, intended-policy interpretation, or operational significance still needs validation.

- **Implementation defect:** Current implementation behavior has a concrete correctness, lifecycle, reliability, or avoidable performance problem. Where a specification is relevant, its actual requirement is cited; a performance concern does not imply an invented complexity guarantee.

- **Unspecified behavior:** The relevant contract leaves an important boundary or failure outcome undefined.

Severity is **High** for wrong-target execution, queue-wide failure, or a misleading failure that can prompt duplicate scene-changing execution; **Medium** for persistent state/artifact leaks, ordinary contract errors, hangs, and input-scaled performance costs. Investigation-lead severity describes conditional impact, not measured incidence.

## High-confidence candidates

### [Fixed] C1. An ordinary pre-dispatch failure aborts the Task scheduler instead of failing its Task

- **Severity:** High.
- **Confidence:** High-confidence candidate.
- **Classification:** Implementation defect.
- **Affected code/symbols:** `src/houbridge/task/runtime.py:106–133`, `:141–169` — `TaskRuntime.run`, `_run_claimed`, `_recover_claimed`, `_validate_or_fail`; `src/houbridge/task/target.py:30–40` — target probing.
- **Relevant specification:** `openspec/specs/task/spec.md`, *Drive queued Tasks through an on-demand background runtime* (117–133), *Bind each Task to the exact Houdini process incarnation selected at submission*, and *Distinguish Python failure from Task Runtime failure* (210 onward). These require queue processing and structured Task runtime failures. The no-replay rules still apply to possibly started invocations.

**Description / why it matters.** `_validate_or_fail` translates only `task_target_changed` into a terminal Task failure. A normal `BridgeError` from the Session probe, such as a transport timeout, is re-raised. Managed-execution lock acquisition also lies outside a per-Task error handler. The exception escapes through `future.result()` and ends the scheduler. The affected Task can remain `queued`, retain its claim, and have no structured runtime error; unrelated queued Tasks stop progressing until another public operation activates a replacement runtime.

With multiple active futures, exiting `ThreadPoolExecutor` waits for the other futures before clearing runtime ownership. Since an already-started caller may legitimately run indefinitely, one pre-start probe failure can also leave the scheduler waiting while no longer scheduling queued work. The appropriate failure boundary therefore depends on whether an invocation may have started; indiscriminately terminalizing recovered work would introduce another error.

**Observed evidence.** `test_probe_failure_escapes_scheduler_and_leaves_both_tasks_queued` used actual Task stores, ownership, claims, runtime, and target validator with two Tasks and concurrency one. A probe adapter raised a representative transport `BridgeError`. Both Tasks remained `queued`, one claim remained, runtime ownership was cleared, and neither Task reached the runner. The scheduler exception escaped. The underlying transport's real timeout error is `hcommand_timeout`; the mechanism is the validator's treatment of any code other than `task_target_changed`.

**Trigger conditions.** A queued Task's PID remains live but its recorded port becomes unreachable; a probe fails transiently; or a managed lock wait fails before caller execution. Other queued work makes the queue-wide effect visible.

**Expected impact.** Stalled queues, repeated failure/recovery cycles for the same unusable target, absent per-Task diagnostics, and blocked progress for unrelated Houdini processes.

**Verification direction.** Exercise real public submission/read flows with one live-but-unreachable target and one healthy target, including concurrency greater than one. Handle known pre-start failures at the Task boundary, record their structured error, and continue scheduling. Test recovery separately so probe failure alone does not authorize replay or abandonment of possibly running Python.

#### Update — 2026-10-03 07:58 — Base 5877496

Verified at the base revision with the existing scheduler probe and new failing regressions: transport-probe and managed-lock failures escaped before dispatch, retaining a queued Task claim. The scheduler now records these known pre-start failures per Task and releases their claims. Recovery tolerates transient probe errors without replay; a recovery lock timeout retains the possibly-running claim and its concurrency slot. Added concurrency-one/two, lock-timeout, and recovery regressions. Independent review confirmed the no-replay and global-concurrency boundaries; parent verification of Task runtime and stream recovery tests passed (30 tests). No native caller cancellation is inferred.

### [Fixed] C2. Fast runtime retirement can erase the only submission-handoff acknowledgement

- **Severity:** High.
- **Confidence:** High-confidence candidate.
- **Classification:** Implementation defect.
- **Affected code/symbols:** `src/houbridge/task/activation.py:81–97` — `TaskRuntimeProcessLauncher`; `src/houbridge/task/runtime.py:123–125` — idle retirement; `src/houbridge/task/runtime_store.py:139–157` — `retire_runtime_if_idle`; `src/houbridge/task/async_submission.py:60–69` — submission failure handling.
- **Relevant specification:** `openspec/specs/task/spec.md`, *Drive queued Tasks through an on-demand background runtime* (117–133); `openspec/specs/command-exec/spec.md`, async submission/handoff requirements (66–83). Successful handoff must return a Task reference, and subsequent execution failure must not retroactively turn submission into failed handoff.

**Description / why it matters.** The launching CLI observes acceptance through the current runtime-owner row. A runtime can claim ownership, execute all available work, and atomically delete that row when retiring. If the parent is not scheduled during the acknowledgement's lifetime, its next inspection sees no matching owner and an exited child, then raises `task_runtime_handoff_failed`. Acceptance is represented by transient ownership rather than durable acknowledgement.

**Observed evidence.** `test_fast_runtime_retirement_is_reported_as_failed_handoff` ran the actual scheduler and shared SQLite ownership/claim/retirement logic before the parent's first acceptance inspection. The worker exited normally; the Task was `completed`; the owner row was absent; the launcher nevertheless raised `task_runtime_handoff_failed`. A runner stub completed the Task to isolate the handoff protocol. The native frequency of this scheduling interleaving was not measured.

**Trigger conditions.** Short work or delayed parent scheduling allows acceptance and idle retirement to occur between parent inspections. This does not require the worker to violate retirement rules.

**Expected impact.** A completed scene-changing operation is reported as failed submission without its Task reference. Retrying that apparent failure can execute the script a second time.

**Verification direction.** Test acknowledgement persistence across worker exit, immediate execution failure, and concurrent submit/retire interleavings. Make the acceptance outcome observable after legitimate retirement while retaining on-demand exit behavior and actual pre-acceptance failure reporting.

#### Update — 2026-10-03 08:38 — Base e78a39e

Reproduced the retired-worker false failure before modification. A clean worker exit with no remaining recoverable work now succeeds; known handoff errors also consult the submitted Task's durable running/terminal state, so another submission after retirement cannot invalidate its acknowledgement. Queued pre-acceptance failures still raise, and unrelated errors are not converted to success. Added real submit/runtime retirement, competing-work, completed/failed outcome, and accepted-running regressions. Independent review checked the acceptance and no-replay boundaries; parent verification passed all 27 Task completion/runtime tests. No schema or public-format changes.

### [Fixed] C3. Host History preflight consumes the async dispatch timeout before dispatch exists

- **Severity:** Medium.
- **Confidence:** High-confidence candidate.
- **Classification:** Implementation defect.
- **Affected code/symbols:** `src/houbridge/task/runner.py:98–123`, `:185–231` — `TaskInvocationRunner.run`, `_monitor`; `src/houbridge/task/invocation_store.py:50–72` — `TaskInvocationStore.create`.
- **Relevant specification:** `openspec/specs/execution/spec.md`, *Separate asynchronous dispatch establishment timeout from Python run duration* (184–198); `openspec/specs/history/spec.md`, *Establish enabled History before Python starts and never replay after start* (313 onward). History preparation is required before caller execution; transport/started-marker establishment has a finite timeout.

**Description / why it matters.** Invocation creation records the current time as `dispatch_started_at`. The runner then performs host History preparation, stages the request and script, and only afterward starts `hcommand`. The monitor derives the finite dispatch deadline from the earlier creation timestamp. Successful source embedding, model initialization, or other slow preflight can exhaust that budget before the fresh dispatch is launched.

**Observed evidence.** `test_task_history_preflight_consumes_dispatch_timeout` used real invocation state and runner logic with a controlled clock. History preparation consumed 10 seconds, with a 5-second transport timeout. The dispatcher then started a live pending transport. At **zero elapsed seconds since dispatch**, the Task became `failed` with `task_dispatch_timeout`, and the new transport was terminated.

**Trigger conditions.** Enabled History preflight or staging takes longer than the finite transport budget, and the started marker is not already present at the first monitor inspection. Cold embedding/model work is a realistic preflight cost; the probe simulated time rather than downloading a model.

**Expected impact.** Valid scripts fail without receiving their configured dispatch establishment interval. A very fast native start creates an additional race between marker publication and the already-expired monitor budget.

**Verification direction.** Distinguish recoverable invocation allocation/preparation time from actual dispatch-establishment time, persist the latter at the appropriate boundary, and test long successful preflight plus prompt caller start. Preserve fail-closed preflight and conservative no-replay behavior across crashes between preparation and dispatch.

#### Update — 2026-10-03 08:59 — Base b8f5896

Verified with the existing controlled-clock probe and a failing regression: 10 seconds of successful History preparation exhausted a 5-second dispatch budget before transport start. The runner now refreshes the existing invocation timestamp after preparation/staging and SQLite transaction acquisition, immediately before dispatch. Timestamp-write errors fail closed before dispatch; recovery retains the conservative creation timestamp if preparation is interrupted. Regression checks cover the full fresh dispatch budget, database-wait skew, persistence failure without dispatch, and conservative recovery. Independent review identified the database-boundary cases before the follow-up fix. Parent verification: 34 Task runtime/stream-recovery tests passed, including unchanged no-post-start-duration coverage; `git diff --check` passed. No schema or public-format changes.

### [ ] C7. A bounded Resource slice loads and decodes the entire payload

- **Severity:** Medium.
- **Confidence:** High-confidence candidate.
- **Classification:** Implementation defect, including avoidable performance cost.
- **Affected code/symbols:** `src/houbridge/resource/reader.py:227–249`, `:318–334` — `ResourceReader.slice`, `_require_text_payload`, `_decode_text`; `src/houbridge/resource/reader.py:203–214` — related metadata-only refusal paths in `get`; `ResourceStore.get_payload`.
- **Relevant specification:** `openspec/specs/resource/spec.md`, *Support bounded UTF-8 slicing* (237–244), explicitly requires decoding and returning only the bounded UTF-8 region, with character offsets and valid boundaries. Resource inspection's fixed output limits are not a license to allocate the full body for every small page.

**Description / why it matters.** Slice first fetches the complete SQLite BLOB and strictly decodes it into a complete Python string. Only then does it take the requested substring. **Observed evidence.** `test_resource_slice_reads_and_decodes_entire_blob` stored a real **16,777,216-byte** ASCII Resource and requested 64 characters at offset 1,024. The memory measurement began after storage/setup; this is one local measurement, not a native or multi-platform benchmark.

**Trigger conditions.** Large text Resources inspected a page at a time, or large payloads refused by ordinary `get`.

**Expected impact.** Approximately O(B) read/decode/copy work and payload-sized transient memory per page of a B-byte Resource. Walking roughly B/L pages of size L repeats approximately O(B²/L) work, despite tiny responses. Character-offset navigation may require scanning UTF-8 boundaries; it does not require full-body decoded-string allocation on every request.

**Verification direction.** Exercise large ASCII and multibyte Resources with fixed small pages while measuring bytes fetched/decoded and allocation peaks. Use metadata before fetching refused bodies, and implement bounded-region access or reusable character-boundary indexing while preserving exact offset/truncation semantics and UTF-8 validity.

### [Fixed] C8. JSON Resource search performs a quadratic span join before returning a small hit window

**Trigger conditions.** JSON with many values/spans and a frequent substring query, particularly arrays or repeated object keys/values. Repeated paging repeats the same join.

**Expected impact.** Rapidly increasing CPU and temporary allocations for otherwise small, bounded Resource search responses.

**Verification direction.** Associate matches with spans through an ordered walk or indexed containment structure; count all logical hits while enriching the requested window. **Trigger conditions.** Repeated recall queries in a long-lived process incarnation with an increasing History entry/change set, even when no new invocation has occurred since indexing.

**Expected impact.** O(E + C) fetching/hydration per query for E entries and C total stored change-body bytes, with payload-sized transient object graphs and database coordination held during the fetches. **Verification direction.** Obtain lightweight ranking metadata and pending IDs first, hydrate lexical change context only for pending entries, and fetch selected detail lazily where required. Test repeated warm queries with many changes and assert no full change-body decoding or index rewrite, while preserving dense source grouping, lexical results, and scene-reset behavior.

- **Confidence:** Plausible candidate; the missing revalidation was exercised, while native port-rebinding incidence remains unmeasured.
- **Classification:** Implementation defect candidate.
- **Affected code/symbols:** `src/houbridge/execution/service.py:29` — initial resolution; `src/houbridge/execution/runtime.py:44–60` — ownership wait, History preflight, staging, dispatch; `src/houbridge/session/resolver.py:57–67` — initial validation; `ResolvedSession.target` — recorded-port transport target.

**Verification direction.** Reproduce controlled native shutdown/rebinding during lock wait and during History preflight. Validate exact identity and probe association immediately before dispatch, and fail on a changed target. Evaluate a wrapper-side expected-process guard for the final probe-to-execution race while keeping caller source behind that guard.

### [ ] P3. Startup timeout scope leaves post-bootstrap verification outside its budget

- **Severity:** Medium.
- **Confidence:** Plausible candidate; behavior is reproduced, but the reasonable bootstrap-only interpretation prevents an unconditional implementation-violation claim.
- **Classification:** Specification defect — timeout-scope ambiguity.
- **Affected code/symbols:** `src/houbridge/session/launcher.py:163–216` — `SessionLauncher._wait_for_bootstrap`, post-bootstrap `probe.inspect`, polling sleep; configured Session probe transport timeout.
- **Relevant specification:** `openspec/specs/session/spec.md`, *Bound session creation and polling* (223–230), specifically describes bootstrap returning a usable automatically selected openport before timeout; `openspec/specs/configuration/spec.md:75–87` independently defines startup, transport, and polling settings.

**Description / why it matters.** The launcher checks its startup deadline in the bootstrap loop, then performs a final probe with its independent transport timeout and returns success without rechecking the startup deadline. Polling sleeps are also not capped to the remaining startup budget. Consequently, the startup setting alone does not bound the time to a validated, registered session. The requirement title suggests bounded creation, while its operative wording can reasonably be read as bounding only automatic-port bootstrap; the contract does not resolve the final-probe budget.

**Observed evidence.** `test_session_startup_can_succeed_after_configured_deadline` supplied an immediately published bootstrap port and a probe advancing a controlled clock by 10 seconds, with startup timeout one second. The actual launcher returned success at clock time 10 without termination. This is a synthetic-clock scope demonstration, not a measured native startup duration.

**Trigger conditions.** Bootstrap publishes a port promptly but final verification is slow; or an unusually large positive polling interval is configured.

**Expected impact.** Operators using the startup timeout as an end-to-end creation budget observe substantially longer waits. Final probing still has a finite independent transport timeout, so this finding does not imply an intrinsically unbounded transport call.

**Verification direction.** State whether startup timeout covers bootstrap only or complete verified creation, and define how final probing and remaining-budget sleeps compose with it. ### [ ] I2. Synchronous pre-terminal transport timeout lacks a demonstrated native ownership/cleanup boundary

- **Severity:** High if native caller execution survives client timeout.
- **Confidence:** Investigation lead.
- **Classification:** Unspecified behavior — native cancellation and managed ownership boundary.
- **Affected code/symbols:** `src/houbridge/houdini/transport.py` — synchronous `subprocess.run` timeout; `src/houbridge/execution/runtime.py:44–90` — lock scope, timeout handling, unconditional workspace removal; execution wrapper output/status publication.

**Description / why it matters.** A synchronous timeout terminates the `hcommand` client subprocess and raises a transport error. **Verification direction.** Run a native script that waits beyond a short transport timeout and then writes independent scene/file markers.
