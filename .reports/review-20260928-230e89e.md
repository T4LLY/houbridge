## High-confidence candidates

**### [Fixed] H1. Task ID reuse after `task reset` collides with History `execution_key` dedup and silently drops the new execution's history entry**

- **Severity:** High
- **Confidence:** High-confidence candidate
- **Classification:** Implementation defect (the `execution_key` dedup mechanism is unspecified; it breaks under spec-sanctioned Task ID reuse)
- **Affected:** `src/houbridge/task/store.py` (`reset`), `src/houbridge/task/history.py` (`AsyncTaskHistory.finalize`), `src/houbridge/history/store.py` (`commit_entry`), interacting with `src/houbridge/history/schema.py` (`history_execution_keys`)
- **Description:** `TaskStore.reset()` deletes `task_semantic_ordinals` (src/houbridge/task/store.py:194), and the task spec explicitly requires ordinal allocation to restart at 000 after a successful reset (openspec/specs/task/spec.md L92–96, L326–331; CLI help text: "Reset terminal task state and task numbering"). Task history finalization commits with `execution_key=f"task:{task.id}"` (src/houbridge/task/history.py:89). `HistoryStore.commit_entry` treats an existing `execution_key` as an idempotent replay: it returns the old `entry_id` and inserts nothing (src/houbridge/history/store.py:183–188). History databases are per process-incarnation and are only retired when the Houdini process incarnation is proven dead (`HistoryRetirementService.retire` via session stale cleanup). Therefore, after `task reset`, a *new* task that re-allocates the same task ID against a *still-alive* session whose history DB already contains `task:<id>` will have its history finalize silently resolve to the old entry: no new history entry, no error, no diagnostic. The task itself completes normally and reports success; only the history record is lost.
- **Why it matters:** Silent data loss in the audit/history record with no error signal — the failure mode is invisible to both the caller and the operator. `execution_key` dedup is presumably intended for genuine retry/replay of the *same* dispatch; task ID reuse after reset produces a *different* execution mapped onto the same key.
- **Evidence:**
  - `src/houbridge/task/store.py:176–194` — `reset()` deletes claims/invocations/stream_chunks/tasks/`task_semantic_ordinals` once all tasks are terminal.
  - `src/houbridge/task/history.py:89` — `execution_key=f"task:{task.id}"` (ID includes the resettable zero-padded ordinal).
  - `src/houbridge/history/store.py:183–188` — `SELECT entry_id FROM history_execution_keys WHERE execution_key = ?` → early `return int(existing["entry_id"])` with no insert and no signal to the caller that this was a collision rather than a replay.
  - `src/houbridge/history/schema.py:47–48` — `history_execution_keys(execution_key TEXT PRIMARY KEY)`.
  - Spec: openspec/specs/task/spec.md L92–96 and L326–331 make ID reuse after reset *specified behavior*; openspec/specs/history/spec.md contains no mention of `execution_key`, dedup, or idempotency (grep verified) — the dedup contract is unspecified implementation behavior.
- **Relevant specification:** task/spec.md (reset semantics, cited above); history/spec.md (silent on execution keys — unspecified).
- **Expected impact:** After any `houbridge task reset` followed by new tasks submitted to a still-attached session (the common case — reset does not restart Houdini), history entries for same-ID tasks are silently dropped whenever the old entry for that key exists in that session's DB. Frequency: every reused ID whose predecessor recorded history.
- **Conditions likely required to trigger:** (1) ≥1 task with history recorded for some task ID; (2) `task reset` succeeds; (3) a new task allocates the same ID for the same semantic base and is dispatched to the same live Houdini incarnation (history DB keyed by pid+identity survives reset).
- **Suggested verification direction:** Unit test: record history for task `X-000`, reset the task store, submit a new task that re-allocates `X-000` against the same history storage, finalize, then assert a *new* entry exists (currently fails: entry count stays 1, second finalize returns the first `entry_id`). Fix direction: include a non-resettable component in the key (e.g. tasks-DB generation/UUID stamped at store creation, or task rowid) instead of the resettable ordinal ID, or make collision-during-finalize raise instead of silently returning.

#### Update — 2026-09-28 19:16 — Base 8723aa2

Verified with a regression reproduction: after recording `history-async-work-000`, terminalizing and resetting Task state, a new `history-async-work-000` finalized into the same live-session History DB left the entry count at 1. The root cause was the resettable Task ID being used as the entire History idempotency key. `AsyncTaskHistory` now adds the invocation-local Temporary Workspace path to the key; that path is stable across recovery of the same invocation and distinct for a new post-reset invocation. Added coverage for both re-finalization idempotency and post-reset ID reuse. Targeted Task/History tests passed (25 tests).

## Plausible candidates

**### [Fixed] P1. History search performs a full O(N) reindex of dense+lexical indexes on every query**

- **Severity:** Medium (performance; degrades with session history size)
- **Confidence:** Plausible candidate (mechanism verified in source; user-visible latency not measured)
- **Classification:** Implementation defect / design issue (spec does not mandate index maintenance strategy — openspec/specs/history/spec.md L216–236 describes the index tables and shared search primitives but is silent on when indexes are synchronized)
- **Affected:** `src/houbridge/history/search.py` (`HistorySearchService.search`, `_synchronize_indexes`), `src/houbridge/search/lexical.py` (`SQLiteFtsIndex.upsert`), `src/houbridge/search/dense.py` (`SQLiteVecIndex.upsert`), `src/houbridge/search/embedding.py` (`SQLiteEmbeddingCache.get` per-hash connection)
- **Description:** Every `history search` invocation calls `_synchronize_indexes(entries, profile)` (src/houbridge/history/search.py:72, 147–183), which: (1) loads **all** entries via `HistoryReader.all_for_search()`; (2) for **each distinct source hash** calls `cache.get(profile, source_hash)` — each call goes through `history_connection_scope`, i.e. a fresh interprocess file-lock acquire + SQLite connection open/teardown; (3) `dense.upsert` rewrites every source-hash vector (executemany DELETE + INSERT, src/houbridge/search/dense.py:85–98); (4) `lexical.upsert` re-indexes **every entry** with ~5 statements each (SELECT fts_id → DELETE fts row → UPSERT entries → SELECT fts_id → INSERT fts full re-tokenization; src/houbridge/search/lexical.py:84–110). All of this is repeated identical work whenever the indexes are already current — which is the steady state after the first search following each commit. Nothing maintains the indexes at commit time, and there is no dirty-set/checksum shortcut.
- **Why it matters:** Concrete cost mechanism — per query: 1 full-table entry load, H file-lock+connection cycles (H = distinct source hashes), 2H vec0 writes, ~5N SQL statements plus N full FTS tokenizations and index writes (N = entry count), all before the actual search executes. For a long-lived session with, say, 500 entries, that is on the order of 2,500+ statements and 500 FTS re-indexings per query, repeated for every query. Latency grows linearly with history size and every query pays it, even consecutive queries with no intervening writes. Contrast: `script_search/service.py::_reconcile` implements exactly the incremental alternative (diff by path/hash/profile, remove stale, upsert changed), demonstrating the pattern is available in-repo.
- **Evidence:** src/houbridge/history/search.py:67 (`all_for_search()`), :72 (`_synchronize_indexes` call per search), :153–157 (factory = `history_connection_scope` per component), :162–171 (per-hash `cache.get` loop), :172 (`dense.upsert(profile, vectors)` with all vectors), :173–182 (`lexical.upsert` over all entries); src/houbridge/search/lexical.py:80–110 (per-doc 5-statement rewrite); src/houbridge/search/dense.py:83–98 (delete+insert all).
- **Relevant specification:** history/spec.md search section (L216–236) — no maintenance strategy specified; per-query full reindex is an implementation choice, not spec-required.
- **Expected impact:** Search latency scales with total session history length rather than query/result size; multi-second searches on large histories; unnecessary lock churn serializes against concurrent history writers.
- **Conditions likely required to trigger:** Any session with a nontrivial number of recorded history entries (cost grows linearly with N per query).
- **Suggested verification direction:** Time `houbridge history search` against a synthetic history DB at N = 50/200/500 entries (expect linear growth in the synchronize phase); profile the statement count. Fix direction: maintain indexes incrementally at finalize time (entries are committed once and immutable) or diff against indexed entry IDs/hashes before rewriting (script_search `_reconcile` pattern).

#### Update — 2026-09-28 19:24 — Base 8723aa2

Verified by tracing `_synchronize_indexes` and a focused reproduction: two consecutive synchronizations over the same two entries performed four embedding-cache reads and rewrote both dense and lexical indexes twice. History entries are append-only, and dense indexing already happens before lexical indexing, so the lexical entry table can safely act as the synchronization marker. `_synchronize_indexes` now queries the indexed lexical entry IDs and only resolves embeddings/upserts dense and lexical records for newly committed history entries. Added a regression test that performs two unchanged searches and asserts the second search does not issue another dense or lexical upsert. Full project tests were not runnable in this environment because optional test/runtime dependencies (`filetype`, `sqlite_vec`) are unavailable; deterministic pre-fix reproduction and syntax verification were used instead.

**### [Fixed] P2. `HistoryRetirementService.retire` acquires the history DB file lock with no timeout — CLI session commands can block indefinitely**

- **Severity:** Medium
- **Confidence:** Plausible candidate
- **Classification:** Implementation defect (reliability; inconsistent with the established lock-timeout pattern applied everywhere else)
- **Affected:** `src/houbridge/history/retirement.py:25–27`; call path: `src/houbridge/cli/session_cmd.py` (info/new/attach/promote wire `_history_retirement_callback` → `retire` during stale-session cleanup)
- **Description:** `retire()` calls `self._file_lock.acquire(history_database_lock_path(...))` with **no `timeout_seconds`** (src/houbridge/history/retirement.py:25–27). `InterprocessFileLock` without a timeout polls forever. Every other history lock site routes through `history_connection_scope` with `lock_timeout_seconds` (config `lock_timeout_seconds`, default 120 s, mapped to `history_lock_timeout` on expiry — the C5/C7 fix pattern). Retirement is reached synchronously from CLI session commands during stale-cleanup, so a wedged or long-held history lock (e.g. a large embedding batch inside `history_connection_scope`, or an abandoned lock holder on a stale mount) hangs `houbridge session info/new/attach/promote` with no bound and no error envelope. The code's own comment says retirement is "explicitly best-effort" — best-effort semantics argue for a bounded wait, not an unbounded one.
- **Why it matters:** An unbounded blocking wait on a best-effort cleanup path inside interactive CLI commands converts a background-contention condition into a permanent CLI hang (until the lock holder releases), with no timeout error the user can act on.
- **Evidence:** src/houbridge/history/retirement.py:17 (`InterprocessFileLock()` default), :25–27 (acquire without `timeout_seconds`); compare src/houbridge/history/locking.py (`history_connection_scope` propagates `lock_timeout_seconds` and maps `InterprocessFileLockTimeout` → `history_lock_timeout`); session CLI wiring per b3 review of `cli/session_cmd.py`.
- **Relevant specification:** openspec/specs/session/spec.md — no lock/timeout requirement for history retirement (unspecified); the global lock-timeout configuration contract (`lock_timeout_seconds`) exists in config and is applied consistently elsewhere.
- **Expected impact:** Any session CLI command that triggers stale-session cleanup blocks indefinitely while any process holds that history DB's file lock.
- **Conditions likely required to trigger:** Stale session detected during a session command + concurrent (or leaked) holder of that session's history lock.
- **Suggested verification direction:** Test: hold the history lock in another process, invoke `session info` with a stale session present, observe unbounded block (vs. expected `history_lock_timeout`-bounded wait). Fix direction: pass `timeout_seconds=lock_timeout_seconds` (or a shorter retirement-specific bound) and treat `InterprocessFileLockTimeout` like `OSError` (return False, best-effort).

#### Update — 2026-09-28 19:37 — Base 8723aa2

Verified from the concrete lock path: `retire()` called `InterprocessFileLock.acquire()` without `timeout_seconds`, and that lock implementation uses no deadline when the argument is omitted. `HistoryRetirementService` now accepts a bounded lock timeout, Session CLI commands propagate the configured `houdini.lock_timeout_seconds`, and `InterprocessFileLockTimeout` is treated as the same best-effort retirement failure as an inaccessible directory. Added a regression test that verifies the timeout is passed to the lock and a timeout leaves stale History in place without failing cleanup. Targeted pytest collection was blocked in this environment by the unavailable `filetype` dependency; syntax compilation and `git diff --check` passed.

**### [ ] P3. Task runner `runtime_failed` drain is not exception-guarded — a stream error skips `mark_runtime_failed` and invocation cleanup**

- **Severity:** Low–Medium
- **Confidence:** Plausible candidate (code path verified; triggering requires a stream-level anomaly at failure time)
- **Classification:** Implementation defect (error-path robustness)
- **Affected:** `src/houbridge/task/runner.py` (`TaskInvocationRunner.runtime_failed`, best-effort drain sequence)
- **Description:** In `runtime_failed`, the "best-effort" stream drain runs **before** `mark_runtime_failed(...)` and `_cleanup_invocation(...)` without its own try/except. The drain path (`TaskStreamCollector.drain`) raises `task_stream_missing` / `task_stream_truncated` / `task_stream_encoding` on stream anomalies (e.g. stream file deleted by an external actor, truncated by disk issues, or non-UTF-8 bytes at final drain). If the drain raises, the exception escapes `runtime_failed`, so the task is never marked `failed`, the invocation row is not removed, and the worker future raises (worker exits). Recovery ultimately occurs via supervisor adoption, but the task sits in `queued`/`running` with no failure record until a new worker adopts it, and the original `runtime_failed` reason (e.g. `task_dispatch_timeout`) is lost.
- **Why it matters:** The failure-handling path itself can fail without leaving terminal state, delaying task terminalization and discarding the primary error code; contradicts the pattern used in `_finalize` (history finalize is wrapped/swallowed) and in `runtime_failed`'s own intent ("best-effort").
- **Evidence:** src/houbridge/task/runner.py `runtime_failed` (drain → mark → cleanup sequence, drain unguarded — see b1/b2 detailed read; contrast guarded swallow of history finalize in `_finalize` and wrapper-failed handling); drain error modes in `src/houbridge/task/streaming.py` (`task_stream_missing`, `task_stream_truncated`, `task_stream_encoding`).
- **Relevant specification:** task/spec.md runtime-failure handling requires tasks to reach terminal failure state; exact drain behavior on corrupted streams is unspecified.
- **Expected impact:** Task remains non-terminal (appears running) until adoption cycle; original failure code replaced by whichever recovery path eventually terminalizes it.
- **Conditions likely required to trigger:** Transport/dispatch failure (path into `runtime_failed`) coinciding with a stream anomaly (missing/truncated/non-UTF-8 stream file). Narrow but concrete.
- **Suggested verification direction:** Unit test: force `runtime_failed` with the stream file deleted; assert task still reaches `failed` with the original code and invocation cleanup occurs. Fix direction: wrap the drain in try/except BridgeError (log-and-continue), keeping mark+cleanup unconditional.

**### [ ] P4. `resource_semantic_aliases` rows are never garbage-collected — unbounded growth after payload expiry**

- **Severity:** Low
- **Confidence:** Plausible candidate
- **Classification:** Implementation defect / unspecified behavior (resource spec defines TTL cleanup for payloads; alias retention policy is unspecified)
- **Affected:** `src/houbridge/resource/store.py` (`cleanup_expired`, `_allocate_alias`), `src/houbridge/resource/schema.py:18` (`resource_semantic_aliases` has no FK to `resources`)
- **Description:** `ResourceStore.cleanup_expired` deletes only `resources` rows (src/houbridge/resource/store.py:270–278). `resource_semantic_aliases` deliberately has no FK to `resources` (so alias→payload joins in `get` simply stop matching after payload expiry, and a re-`put_bytes` of the same content reattaches the old stable alias — a real feature). However, **no code path anywhere deletes alias rows** (verified across resource/* in this review), so every distinct canonical payload ever stored leaves one permanent alias row. Ordinals are allocated as `MAX(ordinal)+1` per prefix, which also means ordinal ranges never compact.
- **Why it matters:** Unbounded, monotonic growth of a global table in `resources.db` for a CLI used over long periods; rows are small (~100 bytes each), so the concrete harm is slow bloat plus ever-growing `MAX(ordinal)` scans — a hygiene/resource-lifetime issue rather than an acute bug, but it has no ceiling and no operator-facing cleanup.
- **Evidence:** src/houbridge/resource/store.py:270–278 (`DELETE FROM resources` only); src/houbridge/resource/schema.py:18 (no FK); grep across `src/houbridge/resource/` shows no `DELETE FROM resource_semantic_aliases`.
- **Relevant specification:** resource/spec.md TTL/retention sections cover payload expiry; alias GC unspecified.
- **Expected impact:** Linear table growth with distinct-payload count for the life of the installation.
- **Conditions likely required to trigger:** Long-term use with many distinct captured/oversized payloads.
- **Suggested verification direction:** Confirm no deletion path exists (grep); decide intended alias lifetime; if aliases are meant to be permanent, document it and cap/compact ordinals; otherwise GC aliases whose canonical payload is expired beyond a grace window.

## Investigation leads

**### [ ] L1. Orphaned `.publish-*` staging files are never cleaned by `cleanup_before`**

- **Severity:** Low
- **Confidence:** Investigation lead
- **Classification:** Implementation defect (minor resource leak)
- **Affected:** `src/houbridge/temporary_artifact.py:76–78` (`cleanup_before` skips any name starting `.publish-`), `src/houbridge/_temporary_fs.py:41–72` (`stage_bytes`/`stage_file` create `.publish-<uuid>.tmp` in the destination namespace directory)
- **Description:** Staging files are unlinked in `finally` blocks on all in-process outcomes, but a hard crash / kill between staging and linking leaves the `.publish-*.tmp` file in the namespace directory. `cleanup_before` explicitly skips all `.publish-` files regardless of age, so orphans accumulate forever. The skip presumably exists to avoid racing in-flight publishes, but an mtime-cutoff check (already computed) would safely distinguish stale orphans from in-flight staging.
- **Evidence:** src/houbridge/temporary_artifact.py:77 (`path.name.startswith(".publish-")` → `continue`), :80 (cutoff available); _temporary_fs.py:43,60 (staging prefix).
- **Expected impact:** Slow temp-dir disk leak proportional to crash frequency.
- **Suggested verification direction:** Kill a capture mid-publish, then run TTL cleanup; assert the orphan remains. Fix: apply the same mtime cutoff to `.publish-` files (with margin).

**### [ ] L2. Task recovery monitor (no dispatcher) lacks phase-2 Houdini-process-exit detection**

- **Severity:** Low
- **Confidence:** Investigation lead
- **Classification:** Unspecified behavior
- **Affected:** `src/houbridge/task/runner.py` `_monitor` phase-2 (recovery mode, `dispatch=None`)
- **Description:** In normal dispatch mode, phase 2 terminalizes on `python-finished` + hcommand process exit. In adoption/recovery mode there is no dispatcher handle, so no exit detection: the loop relies solely on the completion marker or target-death (`_target_is_current` → identity read fails). A wrapper that dies *without* writing markers (e.g. hard crash of hython after `started`, before `python-finished`) while the Houdini *session* stays alive leaves the recovered task monitored forever. Arguably correct-ish (the wrapper's `finally` normally fsyncs markers), hence lead-only.
- **Evidence:** task/runner.py phase-2 loop branches (completion / wrapper-failed / python-finished+exit / target-changed) — no exit branch when `dispatch is None`.
- **Suggested verification direction:** Fault-injection test: adopted task whose Houdini-side wrapper is killed with the parent session alive; observe monitor persists. If confirmed, poll the frozen target pid for exit as a terminalization source.

**### [ ] L3. `collect_outcome` raises bare `RuntimeError` instead of `BridgeError`**
