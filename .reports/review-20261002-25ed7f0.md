### HB-02 — History parameter diff uses key intersection; parameters added/removed after baseline are never recorded — Partially fixed

- **Classification:** Implementation defect (incomplete net-state comparison), with a secondary specification gap (no vocabulary for parm addition/removal)
- **Severity:** Medium (silent data-completeness loss in Action History)
- **Confidence:** Medium-high at code level (behavior is unambiguous); runtime impact pending Houdini verification

**Evidence:**

- `src/houbridge/houdini/scripts/history/action_recorder.py:234-244` — `_parm_changes` iterates `sorted(old.keys() & new.keys())` (intersection only). A parameter present in the after-state but absent from the baseline (or vice versa) produces no `parm_changed`.
- Contrast `action_recorder.py:262-272` — `_input_changes` iterates `old.keys() | new.keys()` (union), so newly acquired inputs *are* captured. The asymmetry indicates the intersection in `_parm_changes` is an oversight rather than a deliberate rule.
- Affects both the existing-node path (`:216`) and the created-node path (`:228`).

**Spec sections:** `openspec/specs/history/spec.md:137` (baseline contains parameter raw values), `:148` ("records the parameters whose Before/After states differ"), `:168` ("Existing nodes SHALL be compared from execution-start baseline to execution-end state"), `:195` (per-component comparison so differing components are represented).

**Impact:** Caller Python that appends/removes multiparm rows (foreach, copy-stamp, agent groups), adds spare parameters, or sets newly-created instance parameters produces a History entry that omits those changes entirely. The History then understates the net state change, and search/diff consumers cannot see parameter additions/removals that materially define the scene delta.

**Trigger conditions:** Any `exec`/async task with History enabled whose source modifies the parameter *set* of a node that existed at baseline (or of a node created earlier in the same execution), rather than only mutating pre-existing parms.

**Verification direction:** In a real Houdini session: create a node with a multiparm (e.g., `attribute_wrangle` with user-added spare parm, or a foreach/`copy` with variable block count), run `houbridge exec` code that appends a multiparm instance and sets its value, then `houbridge history get` and confirm the new parm is absent from `parm_changed` records. If confirmed, decide the representation for added/removed parms (e.g., before/after of `""` vs value, or an explicit omission rule in `history/spec.md`) and switch `_parm_changes` to union-key iteration with a defined missing-key semantic.

### HB-03 — Recovered invocations cannot detect a dead wrapper; Task can stay `running` indefinitely while the Houdini session lives — Deferred

- **Classification:** Unspecified behavior (spec-mandated monitor loop has no wrapper-liveness signal in the recovery path)
- **Severity:** Low-medium (operational hang, bounded by Houdini session lifetime)
- **Confidence:** Medium

**Evidence:**

- `src/houbridge/task/runner.py:235-260` — `_monitor` loop 2: with `dispatch is None` (recovery path via `TaskInvocationRunner.recover`), the loop waits on completion/wrapper-failed markers and the periodic target-identity check only. There is no process handle to poll, so a wrapper (hcommand) that died *without* writing `wrapper-failed.json` (e.g., killed by an OS OOM killer, hard crash) leaves the invocation monitored forever.
- Live dispatch is protected: `runner.py:200-232` polls the Popen and converts pre-start/pre-completion exit into `houdini_transport_failed` / `task_wrapper_failed`. The recovery path has no equivalent.

**Spec sections:** `openspec/specs/task/spec.md:227-229` — "If a replacement runtime observes a started Task without a completion marker while the bound Houdini PID is still valid, it SHALL monitor/finalize that existing invocation… Absence of a Python-finished marker SHALL NOT create a wall-clock timeout for caller Python. If the bound process is no longer valid, the Task SHALL become `failed`." The spec defines remediation only for target death, not for wrapper death with a live target.

**Impact:** A stuck `running` task holds its concurrency claim indefinitely (consuming one of `[task].max_concurrency` slots), cannot be cleaned by TTL (retention applies to terminal tasks only), and blocks `task reset` (which refuses while queued/running work exists). Recovery occurs only when the Houdini session eventually exits (target check fails the task) or an operator intervenes directly in `tasks.db`.

**Trigger conditions:** Task Runtime crash/upgrade after `started.json` is published but before completion, followed by the hcommand wrapper process dying abnormally (no `wrapper-failed.json`) while the Houdini session stays alive.

**Verification direction:** Reproduce: submit an async task; kill the Task Runtime worker; kill the hcommand child process (not Houdini); restart the worker via `task get`; observe the recovered invocation polling forever. Then specify the desired semantics — e.g., a durable wrapper PID/incarnation recorded in `task_invocations` so recovery can detect orphaned wrappers, or a heartbeat in the wrapper — and extend `task/spec.md:229` accordingly before changing code.

#### Update — 2026-10-03 02:33 — Base 02e668a

- Re-read the monitor path and independently reran four bounded diagnostics at this base: **4 passed in 1.66s**. Started invocations without terminal markers stayed running for five deterministic polls, both with and without `python-finished.json`; the live target, claim, workspace, blocked reset, and TTL exclusion persisted, with zero replay. No markers at all instead reached `task_dispatch_timeout`; a changed target reached `task_target_changed` and released state.
- Corrected the trigger interpretation without altering the original review: post-start live dispatch polls its handle only after Python-finished evidence, so it is not generally protected against earlier wrapper exit. Recovery has no dispatch handle. Killing the hcommand client is not established as proof that Houdini-side caller Python stopped.
- Current persistence records target and runtime-owner identities, not authoritative per-invocation wrapper liveness. A safe remedy needs agreed failure evidence and specification/persistence decisions while preserving no replay and unbounded caller Python. The relevant Task code and specification are unchanged from the initial investigation base `70839fc`.
- The user selected deferral of this redesign. No production/test/persistent-format change or arbitrary timeout was introduced; this report-only disposition is accumulated for the final documentation commit. Native Houdini process-kill behavior remains unverified.

### HB-04 — sqlite-vec KNN retrieves `k` rows before membership filtering, under-sampling filtered dense search — Fixed

- **Classification:** Unspecified behavior / potential recall defect
- **Severity:** Low
- **Confidence:** Lead only

**Evidence:** `src/houbridge/search/dense.py:112-140` — `search_scored` issues `embedding MATCH ? AND k = ?` with an optional `entry_id IN` membership filter (`append_membership_filter`). In sqlite-vec's KNN constraint model, `k` bounds rows *fetched*, and the membership predicate is applied by SQLite as a post-filter, so excluded documents (top-level `_`-prefixed scripts, filtered by `script_search/service.py` at query time) can occupy the top-k and crowd out eligible candidates.

**Spec sections:** `search/spec.md` (hybrid retrieval quality expectations), `script_search` filtering behavior from `changes/` filtering work.

**Impact:** Reduced recall for `houbridge search script` when underscore-filtered scripts dominate the dense neighborhood; deterministic and silent.

**Verification direction:** Construct a fixture index where >k filtered-out documents are nearest to the query; assert result sets with/without the filter. If confirmed, raise the internal `k` (e.g., `k = candidate_limit * oversample` when a filter is present) or filter ids post-query with an enlarged fetch; check sqlite-vec version semantics for rowid-in-KNN support.

### HB-05 — Python-level stdout/stderr redirection does not capture C-level file-descriptor writes — Unverified

- **Classification:** Unspecified behavior
- **Severity:** Low
- **Confidence:** Lead only

**Evidence:** `src/houbridge/houdini/scripts/execution/runtime.py:71` and `src/houbridge/houdini/scripts/task/runtime.py:71` use `contextlib.redirect_stdout/redirect_stderr`. Writes performed by C extensions directly to OS file descriptors 1/2 (SOP cook diagnostics, VEX warnings, native library prints) bypass the Python-level `sys.stdout`/`sys.stderr` swap. Under `start_script`/`execute_script` those descriptors point at `DEVNULL` (transport), so such output is silently discarded rather than captured into the invocation's stdout/stderr streams — in both sync and async modes.

**Spec sections:** `execution/spec.md` (stdout/stderr capture contract — silent on fd-level semantics); `task/spec.md:182-197`.

**Impact:** Caller-visible Houdini-native diagnostic output may be missing from `exec` results and `task get` streams, hampering debugging without affecting correctness of the declared result.

**Verification direction:** In Houdini, run a `houbridge exec` snippet that triggers native cook warnings (e.g., VEX compile error) and compare against a `print()` from Python. If output is lost, evaluate `os.dup2`-based fd redirection onto the stream files in the injected runtimes (careful with restore-on-exception and Houdini's own console expectations), and record the chosen semantics in the execution spec.
